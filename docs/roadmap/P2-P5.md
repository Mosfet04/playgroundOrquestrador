# P2 a P5 — nível de fase

Detalhadas em itens quando a fase começar (e o FA correspondente do orquestrador estiver concluído). Contrato da API Admin: `../orquestradorIAPythonArgo/docs/roadmap/FA-admin-config.md`.

## P2 — BFF e auth (depende de FA-02)

P2-01 env validado com zod em `src/server/env.ts` (`server-only`); login de usuário único (senha via env, comparação em tempo constante, rate limit simples), cookie de sessão assinado com `jose` (`httpOnly`, `Secure`, `SameSite=Lax`), `middleware.ts` protegendo páginas e `/api/*`, checagem de `Origin` em mutações, sem open redirect no `?next=`. P2-02 `src/server/orchestrator/`: cliente tipado (timeout, mapeamento de erro sem eco, chave admin/run no header), tipos gerados por `openapi-typescript` a partir do snapshot `docs/contracts/orchestrator-openapi.json` (script `contract:update` + checagem de divergência na CI). P2-03 chat via BFF: route handler `runtime = 'nodejs'` que repassa o stream de runs com abort propagado ao orquestrador; endpoint do orquestrador só no servidor (sai o campo de endpoint do Sidebar); `user_id` vem da sessão (saem FingerprintJS e `api.ipify.org`); exclusão de sessão com a chave admin no servidor. P2-04 markdown seguro (`rehype-raw` sai; `rehype-sanitize` com schema estrito; links só `http(s)`/`mailto`). P2-05 dashboard pelas rotas do AgentOS/orquestrador; remove `src/lib/mongodb.ts`, o pacote `mongodb` e as rotas de dashboard que leem o Mongo (o que faltar de métrica fica para a F8 do orquestrador).

## P3 — Editores com paridade (depende de FA-02, FA-03, FA-05, FA-06)

P3-01 formulário dirigido por `/admin/schema` (providers, `model_params` aceitos por provider, modos de team, tipos de parâmetro, formatos de referência de segredo) com react-hook-form + zod gerado do schema; erros 422 por campo do orquestrador mostrados no campo. P3-02 editor de agent (identidade, modelo, `model_params`, `base_url`, `api_key_ref`, instruções, memória, resumo, tools). P3-03 editor de tool HTTP (rota com `{param}`, parâmetros tipados com `default_value`, headers por referência e mascarados, preview da requisição). P3-04 editor de team (novo: membros, modo route/coordinate/broadcast/tasks, modelo líder, memória). P3-05 RAG (`doc_name`, embedder, `search_strategy`, params) e seletor de segredo `env:`/`file:` reutilizado por modelo, embedder e header. P3-06 concorrência e exclusão: `If-Match`/ETag, tela de conflito no 412 (recarregar ou comparar), desativar (soft) e excluir (hard, com confirmação). Ao fim da fase, as rotas `src/app/api/{agents,tools}` que falam com o Mongo saem.

## P4 — UX realtime (depende de FA-04, FA-05)

P4-01 status após salvar: "aplicado na revisão N" / "falhou: <motivo do orquestrador>" (o runtime anterior continua no ar); indicador global da revisão do runtime. P4-02 diff do que muda antes de salvar. P4-03 "Testar agora": abre o playground com a entidade recém-salva numa sessão nova. P4-04 histórico de alterações (auditoria) com restaurar versão. P4-05 `/settings`: providers disponíveis, config store (Mongo/YAML só leitura), versão e saúde do orquestrador.

## P5 — Fase B (depende de FA-07 e da F4-02 do orquestrador)

P5-01 campos de agent/team que hoje são fixos no orquestrador (`markdown`, `num_history_runs`, `add_datetime_to_context`, `reasoning`...), entrando no formulário pelo `/admin/schema` sem código por campo. P5-02 tools MCP (quando o cliente MCP da F4-02 existir).
